### Pipeline narrative

The batch estate is one daily ledger cycle plus a handful of periodic and utility jobs. Three sources describe the ordering and they agree: `scripts/run_full_batch.sh` (the canonical developer run), the CA-7 listing (`CardDemo.ca7`, SCHID 030/031/032 chains) and the Control-M export (`CardDemo.controlm`, DAILY / WEEKLY / MONTHLY folders). Read them together and the pipeline is:

**Phase 0 — quiesce CICS.** `CLOSEFIL` (SDSF `CEMT SET FILE ... CLOSED`) is the first job of every chain, and `OPENFIL` is the last; every chain passes through `WAITSTEP` (`COBSWAIT` → `MVSWAIT` assembler) before `OPENFIL` to let the VSAM closes settle. Everything between them runs with the online application unable to touch the KSDS files.

**Phase 1 — reference/master refresh (idempotent).** `ACCTFILE`, `CARDFILE`, `XREFFILE`, `CUSTFILE`, `DISCGRP`, `TCATBALF`, `TRANTYPE`, `TRANCATG`, `DUSRSECJ` each DELETE/DEFINE a KSDS (plus AIX + PATH for CARDDATA, CARDXREF, TRANSACT) and REPRO the `.PS` seed file into it. `TRANFILE` does the same for the ledger from `DALYTRAN.PS.INIT`. With the DB2 extension installed, `TRANEXTR` (DSNTIAUL) unloads `CARDDEMO.TRANSACTION_TYPE[_CATEGORY]` into `TRANTYPE.PS` / `TRANCATG.PS` first, so DB2 is the system of record and VSAM is a nightly projection. These jobs have no inter-dependencies except that the AIX jobs need their base cluster; in the run script they are simply sequential.

**Phase 2 — backup.** `TRANBKP` REPROs `TRANSACT.VSAM.KSDS` → `TRANSACT.BKUP(+1)` (GDG). It runs twice in the daily script: once before posting (recovery point) and once after interest so `COMBTRAN` has a current sequential image of the ledger.

**Phase 3 — posting (`POSTTRAN` → `CBTRN02C`).** Reads `DALYTRAN.PS` sequentially and, per record, validates via `CARDXREF` (reason 100) and `ACCTDATA` (101 not found, 102 over-limit, 103 after account expiry). Valid records are written to `TRANSACT.VSAM.KSDS`, added into `TCATBALF` (creating the account/type/category row on first sight) and applied to `ACCTDATA` (`CURR-BAL`, and `CYC-CREDIT` or `CYC-DEBIT` by sign). Rejects go to `DALYREJS(+1)` with an 80-byte reason trailer. Note that `DALYTRAN.PS` is an *input* to the estate: nothing in the repository produces it. In particular the IMS pending-authorization database written by `COPAUA0C` is never read by any batch program other than the purge (`CBPAUP0J`), so there is no authorization → settlement → posting bridge; `PA-MATCH-STATUS = 'M'` is defined but never set.

**Phase 4 — interest (`INTCALC` → `CBACT04C`, monthly in Control-M).** Reads `TCATBALF` in key order; per (account, type, category) looks up the rate in `DISCGRP` by `ACCT-GROUP-ID` with fallback to group `DEFAULT`, computes `balance × rate / 1200`, and emits a system transaction (`TYPE 01 / CAT 05`, id = run-date parm + suffix) to the sequential `SYSTRAN(+1)`. On account change it adds the accumulated interest to `ACCT-CURR-BAL` and **zeroes both cycle buckets** — this is the statement-cycle close. `1400-COMPUTE-FEES` is an empty stub.

**Phase 5 — merge (`TRANBKP` → `COMBTRAN`).** `COMBTRAN` SORT-merges `TRANSACT.BKUP(0)` with `SYSTRAN(0)` on `TRAN-ID` into `TRANSACT.COMBINED(+1)` and REPROs it back over `TRANSACT.VSAM.KSDS` (REPLACE). Interest transactions are now on the ledger. `TRANIDX` then rebuilds the AIX on `TRAN-PROC-TS` so `COTRN00C`/`CORPT00C` can browse by date.

**Phase 6 — reporting / statements (on demand, CA-7 SCHID 030/031).** `CREASTMT` SORTs the ledger by card number into `TRXFL` and runs `CBSTM03A` (+`CBSTM03B` for file I/O) to produce `STATEMNT.PS` and `STATEMNT.HTML`; `TXT2PDF1` converts the text file. `TRANREPT` (submitted from CICS by `CORPT00C` through the internal reader, with `DATEPARM` from the screen) unloads the ledger via `REPROC`, SORTs the date range into `TRANSACT.DALY(+1)` and runs `CBTRN03C` for the paginated report. `PRTCATBL` dumps `TCATBALF`.

**Side chains.** `CBPAUP0J` (CA-7 SCHID 030, before `POSTTRAN`) runs the IMS BMP `CBPAUP0C` to DLET expired `PAUTDTL1` segments and empty `PAUTSUM0` roots. `CBEXPORT`/`CBIMPORT` are a branch-migration utility pair (`EXPORT.DATA` multi-record file). `READACCT/READCARD/READCUST/READXREF` (CA-7 chain) are read-and-print smoke tests; `READACCT` also writes the COMP / ODO / VB layout variants used by the "complex copybook" demo. The IMS `UNLDPADB → LOADPADB` and `UNLDGSAM` jobs are DBA unload/reload utilities, not part of the business cycle.

**What the lineage tells a modernisation team.**
- Every business dataset has exactly one writer program in the daily cycle: `ACCTDATA` (CBTRN02C, CBACT04C — plus COACTUPC/COBIL00C online), `TCATBALF` (CBTRN02C), `TRANSACT` (CBTRN02C, COMBTRAN merge — plus COTRN02C/COBIL00C online). Ownership boundaries for a service decomposition are therefore clean.
- The GDGs (`TRANSACT.BKUP`, `SYSTRAN`, `COMBINED`, `DALYREJS`, `TRANSACT.DALY`, `TRANREPT`) exist only to move data between steps; none is read by online code. In a Java/relational target they collapse into transactional writes and a rejects table.
- `CLOSEFIL`/`OPENFIL`/`WAITSTEP` encode the fundamental constraint of the legacy design — batch and online cannot share the files. Removing that constraint (row-level locking) is the main operational win of the migration and should drive the sequencing: post transactions first, since it is the only job that must currently take the online system down every night.
