# CardDemo COBOL → Java Migration: Test Strategy

This document defines how we prove that the migrated Java application behaves exactly
like the CardDemo COBOL/CICS application. It is backed by three companion artifacts:

| Artifact | Purpose |
|---|---|
| [`golden_data/`](golden_data/) | Canonical JSON fixtures decoded from `app/data/ASCII/*.txt` (plus the EBCDIC export file), and `manifest.json` with record counts, control totals, key ranges, referential checks and source checksums. Generated by `golden_data/tools/generate_golden.py` (deterministic; `--check` verifies the committed output). |
| [`test_harness/`](test_harness/) | Maven/JUnit 5 module: copybook codec, loaders, field/byte comparators, reconciliation engine, and the migrated-application integration point (currently a stub). |
| [`reconciliation_checks.md`](reconciliation_checks.md) | Catalogue of every dataset-level and program-level validation, with tolerance and non-comparable-field policy. |
| [`test_harness/traceability/rule_inventory.csv`](test_harness/traceability/rule_inventory.csv) | Rule-to-test traceability matrix extracted from `app/cbl` by `test_harness/scripts/extract_rules.py`. |

Guiding principles:

1. **The COBOL source and copybooks are the specification.** Where behavior looks like a
   bug (several are listed below), the migration reproduces it unless a signed-off
   decision record says otherwise; the parity test then encodes the decision.
2. **Files and records are the contract.** The harness never links against application
   classes. The migrated app is exercised through its file inputs and outputs (batch) and
   COMMAREA/BMS-equivalent request/response payloads (online).
3. **Exact decimal arithmetic.** All amounts are compared as `BigDecimal` canonical
   strings; there is no floating-point tolerance anywhere.
4. **Deterministic fixtures.** Every generated artifact is reproducible byte-for-byte and
   guarded by a `--check` mode.

## 1. Layered approach

```
 L3  End-to-end parity      online COMMAREA/BMS replay (CO*) + full nightly batch + reconciliation
 L2  Job-chain tests        CBTRN01C → CBTRN02C → CBTRN03C → CBSTM03A/B ;  CBEXPORT → CBIMPORT
 L1  Rule-level golden      one suite per program, one case per extracted rule/branch
 L0  Harness self-tests     codec / loader / compare / recon against golden_data (runs today)
```

### L0 — Harness self-tests (available now)

Runs with no application present (`mvn -f test_harness/pom.xml verify`):
copybook layout conformance against `manifest.json`, Java decode of every raw record equals
the golden JSON (cross-implementation check against the Python reference decoder),
decode→encode byte round trip for every record, EBCDIC/ASCII parity, mutation detection,
manifest reconciliation and recon-engine unit tests. The migrated-app parity test is
reported as **skipped** until an adapter is configured (see §8).

### L1 — Rule-level golden tests per program

For each program in `app/cbl` one test class drives the migrated equivalent of that
program with minimal fixtures that isolate a single rule from the inventory (§2). Each
case is identified by the `test_case_id` column of the traceability matrix
(e.g. `L1-BATCH-CBTRN03C-R021`). Expected outputs come from one of two oracles, in this
order of preference:

1. **Reference run** of the COBOL program (z/OS, AWS Mainframe Modernization, or GnuCOBOL
   with the same copybooks) on the case fixture, captured byte-for-byte.
2. **Source-derived expectation** written by a reviewer from the COBOL statement, marked
   `oracle=derived` in the matrix until confirmed by a reference run.

Batch cases supply input files built from golden records (encoded with the harness codec)
and assert on output files, return code, abend code and `DISPLAY` lines that carry
business meaning (counts, statuses). Online cases (`CO*`) supply a COMMAREA plus mapped
BMS input fields and assert on the returned COMMAREA, BMS output fields/attributes, the
`XCTL`/`RETURN TRANSID` target and VSAM side effects.

### L2 — Job-chain tests

| Chain | JCL | What is chained | Key assertions |
|---|---|---|---|
| Posting chain | `POSTTRAN.jcl`, `TRANREPT.jcl`, `CREASTMT.JCL` | `CBTRN01C` (validation/lookup driver) → `CBTRN02C` (posting: TRANSACT, DALYREJS, ACCTDATA, TCATBALF) → SORT by `TRAN-CARD-NUM` → `CBTRN03C` (report) → SORT by card/tran id → `CBSTM03A` + `CBSTM03B` (statements) | posted + rejected = input; reject-reason parity; balance recomputation; report page/account/grand totals; statement totals = detail sums |
| Interest | `INTCALC.jcl` | `CBACT04C` over TCATBALF with DISCGRP lookup (fallback `DEFAULT`) | interest = `TRAN-CAT-BAL × DIS-INT-RATE / 1200` (truncated, no `ROUNDED`); generated TRAN records; account balance += total interest, cycle credit/debit reset |
| Export/import | `CBEXPORT.jcl`, `CBIMPORT.jcl` | `CBEXPORT` (customer, account, xref, transaction, card → 500-byte multi-record EXPORT file) → `CBIMPORT` (split back by `EXPORT-REC-TYPE`) | record count per type; split files equal export source datasets field-by-field; unknown record type routed to error file; byte round trip of the EXPORT file |

Intermediate files are compared at every hop (not only at the end of the chain) so a
divergence is localized to one program.

### L3 — End-to-end parity

* **Online replay.** Captured CICS interactions (COMMAREA in/out, BMS map in/out, AID key,
  `EIBCALEN`, RESP/RESP2) for every `CO*` program — sign-on (`COSGN00C`), menus
  (`COMEN01C`, `COADM01C`), account view/update (`COACTVWC`, `COACTUPC`), card
  list/view/update (`COCRDLIC`, `COCRDSLC`, `COCRDUPC`), transactions (`COTRN00C-02C`),
  bill pay (`COBIL00C`), report submit (`CORPT00C`), users (`COUSR00C-03C`) — are replayed
  as scripted sessions against the Java app. Screen fields are compared after attribute
  normalization; pseudo-conversational state is compared through the COMMAREA.
* **Full nightly batch.** The scheduler definition in `app/scheduler` drives the whole
  batch on a cloned golden database (all nine VSAM datasets); every output dataset is
  compared field-by-field and byte-by-byte.
* **Reconciliation.** `ReconciliationEngine` runs the checks in
  [`reconciliation_checks.md`](reconciliation_checks.md) on the before/after images.

## 2. Business-rule inventory methodology

### 2.1 Extraction

`test_harness/scripts/extract_rules.py` scans the PROCEDURE DIVISION of every program in
`app/cbl` (31 sources: 12 `CB*` batch, 18 `CO*` online, plus utility `CSUTLDTC`; the
request referred to "30 programs" — the inventory covers all 31 files actually present)
and emits one row per:

| Kind | Statements |
|---|---|
| decision | `IF`, `EVALUATE`, `WHEN`, `INVALID KEY`, `NOT INVALID KEY`, `AT END`, `ON SIZE ERROR`, `NOT ON SIZE ERROR`, `PERFORM … UNTIL` |
| arithmetic | `COMPUTE`, `ADD`, `SUBTRACT`, `MULTIPLY`, `DIVIDE` |

Rules: comment lines (indicator `*` or `/`) and `EXEC CICS/SQL/DLI … END-EXEC` blocks are
skipped, string literals are blanked before matching, `END-IF`/`END-EVALUATE` are not
counted, and every row is attributed to its enclosing paragraph. Rows get a stable ID
`<PROGRAM>-R<nnn>` and a planned test case ID `<LAYER>-<rule id>`. Run with `--check` in CI
to fail when the matrix is stale after a source change.

Current extraction (see `rule_inventory_summary.md` for the per-program table):
**1,673 rules** — 774 `IF`, 113 `EVALUATE` with 622 `WHEN`, 12 `INVALID KEY`, 4
`NOT INVALID KEY`, 30 `PERFORM … UNTIL`, 32 `COMPUTE`, 75 `ADD`, 11 `SUBTRACT`. There are
no `ON SIZE ERROR` clauses in the main application; arithmetic overflow is therefore
silent truncation in COBOL and must be tested explicitly (§6).

### 2.2 Enrichment (manual, per program)

The extractor finds statements; analysts add what a regex cannot: the business meaning,
the branch outcomes to cover (each `IF` → true/false; each `WHEN` → taken; each
`INVALID KEY` → hit/miss), implicit control flow (`NEXT SENTENCE`, `GO TO`, `ALTER` in
`CBSTM03A`), and the oracle. Status moves `PLANNED → DERIVED → CONFIRMED` (reference run
captured) `→ PASSING` (Java matches).

### 2.3 Traceability matrix

Columns of `rule_inventory.csv`:

`rule_id, program, source, paragraph, line, kind, category, statement, test_layer,
test_case_id, chain_level, status`

The matrix is the coverage ledger: a program is "migrated" only when every row is
`PASSING` or covered by an approved waiver. L2/L3 cases reference the rule IDs they
exercise so a failing chain test points back to rules.

### 2.4 Worked examples from `app/cbl/CBTRN03C.cbl`

| Rule (matrix ID) | Source | Behavior | Test cases |
|---|---|---|---|
| Date-range filter (`R003`) | lines 173-178 | `IF TRAN-PROC-TS (1:10) >= WS-START-DATE AND TRAN-PROC-TS (1:10) <= WS-END-DATE CONTINUE ELSE NEXT SENTENCE`. Comparison is alphanumeric on the first 10 bytes of the timestamp (`YYYY-MM-DD`), inclusive at both ends. `WS-START/END-DATE` come from the DATEPARM record (`X(10)`, `X(1)` filler, `X(10)`). | Records on start date, on end date, one day before, one day after; malformed timestamp (e.g. `2022/01/01`) compares by collating sequence, not as a date; start > end produces an empty report. **`NEXT SENTENCE` subtlety:** it transfers control past the next separator period, which is the one after `END-PERFORM` (line 207) — i.e. the first out-of-range record ends the read loop and no page/grand totals are written. This is source-derived and must be confirmed by a reference run; the case is tagged `HIGH-RISK`. |
| Page break via `FUNCTION MOD` (`R021`) | lines 282-285, 292-303 | Before each detail line, `IF FUNCTION MOD(WS-LINE-COUNTER, WS-PAGE-SIZE) = 0` writes page totals and headers. `WS-PAGE-SIZE` = 20 (`9(03) COMP-3`). | Exactly 16 details on page 1 (headers = 4 lines), 14 details per subsequent page (page totals 2 + headers 4 lines); page totals reset to 0 and roll into grand total. |
| Line counter counts non-detail lines | lines 299/302 (page totals), 311/314 (account totals), 327-339 (4 header lines), 373 (detail) | Headers, page totals and account totals all increment `WS-LINE-COUNTER`. | `WS-FIRST-TIME` header logic (`R006`, `R020`) | lines 128, 181-188, 275-280 | First detail writes the headers and copies the date range into the header; account totals are suppressed on the very first card-number change (`IF WS-FIRST-TIME = 'N'`). | Empty input → no header at all; single transaction → header + detail; first card break does not emit a zero account total. |
| Group-break by card number (`R005`) | lines 181-188 | Account totals are triggered when `TRAN-CARD-NUM` changes (not account ID); `TRANREPT.jcl` sorts by card number first. | Unsorted input → repeated groups for the same card (parity, not "fix"); two cards of one account → two account-total blocks. |
| End-of-file totals | lines 197-205 | On EOF the last `TRAN-AMT` (still in the record area) is added **again** to page/account totals before page and grand totals are written; the last account total is not written. | Single-record and multi-record files: grand total = Σ amounts + last amount (source-derived, confirm by reference run). |
| File-status `EVALUATE` (`R014`-`R017`) | lines 251-258 | `'00'` → `APPL-RESULT` 0 (process); `'10'` → 16 (EOF, sets `END-OF-FILE`); other → 12 → display status and abend. | Status 00, 10, and a forced other (e.g. `'35'` missing file, `'39'` attribute mismatch) → abend 999. |
| INVALID KEY abends (`R047`-`R049`) | lines 484-511 | Missing CARDXREF, TRANTYPE or TRANCATG key → `DISPLAY`, `IO-STATUS` = 23, `9999-ABEND-PROGRAM` (`CEE3ABD` code 999). | One case per lookup; assert abend code 999, the displayed key, and that output written so far matches (partial report). |

The same treatment applies to `CBTRN02C` (reject reasons 100 invalid card, 101 account
not found, 102 over limit, 103 expired — note 103 overwrites 102 because both checks run;
109 account rewrite failure occurs **after** the category balance was updated), and
`CBACT04C` (DEFAULT disclosure-group fallback; truncating interest computation; last
account updated on EOF).

## 3. Coverage proof

| Dimension | Method | Exit criterion |
|---|---|---|
| Rule coverage | Every `rule_inventory.csv` row has ≥ 1 L1 case; every decision row has a case per branch outcome. | 100 % of rows `PASSING` or waived. |
| Java branch coverage mapped to COBOL paragraphs | JaCoCo on the migrated app during L1/L2; each Java method carries a `@CobolParagraph("CBTRN03C", "1100-WRITE-TRANSACTION-REPORT")` style annotation (or a mapping file). A report joins JaCoCo branch counters to paragraphs. | Every COBOL paragraph reached; ≥ 95 % branch coverage per mapped paragraph; uncovered branches listed against rule IDs. |
| Field-level coverage | For every field in the 10 copybook layouts (manifest `layout` rows), at least one test asserts a non-default value and at least one comparison detects a change in it. Implemented by `MutationDetectionTest` (rotates the mutated field across records so all fields are hit). | Every non-FILLER field covered; FILLER covered by byte round trip. |
| Mutation checks | For every golden record, corrupt one field (alpha char change, numeric +1 unit at scale, sign flip) and, separately, one byte (sign nibble, packed nibble, overpunch char). Comparator/round trip must flag exactly that field. | 100 % of mutants detected. |
| Reject/abend parity | Counts per reject reason (100/101/102/103/109), return codes (0/4), abend codes (999) and file statuses match the reference run. | Exact equality. |

The harness itself is measured with JaCoCo (`test_harness/target/site/jacoco`).

## 4. Data-format handling

### 4.1 Decode-to-canonical-JSON strategy

Raw records are decoded strictly per copybook PIC/USAGE into JSON (rules recorded in
`golden_data/manifest.json` → `conventions`):

* One JSON array per dataset, one object per record, keys = COBOL field names in copybook
  order; group levels flattened (elementary names are unique per layout).
* Numerics → canonical decimal **strings** (`"-12.30"`, `"0.00"`): optional `-`, no
  leading zeros, exactly the PIC scale. Width is not stored — the encoder re-derives it
  from the PIC, so `ACCT-ID "1"` re-encodes to `00000000001`.
* `PIC X` → verbatim string, trailing spaces kept; dates/timestamps stay raw strings
  (no date parsing — invalid dates must survive the round trip).
* `OCCURS` → array of objects; `FILLER` → kept verbatim (needed for byte round trip).
* `REDEFINES` → the branch selected by the discriminator (`EXPORT-REC-TYPE` C/A/X/T/D) is
  decoded; non-discriminated views (`EXPORT-TIMESTAMP-R`) are omitted.
* Anything that cannot be decoded under its PIC becomes
  `{"$type": "<ZONED|PACKED|BINARY|ALPHANUMERIC|…>", "hex": "<source bytes>"}` and is
  re-encoded from the hex. Real example: `EXP-ACCT-ADDR-ZIP` / `EXP-ACCT-GROUP-ID` contain
  LOW-VALUES (`x'00'`) in export records 50 and 99.

### 4.2 PIC-type handlers

| PIC / USAGE | Storage | Decoder rule | Encoder rule |
|---|---|---|---|
| `X(n)` | n bytes | ASCII or CP037 text; control bytes (e.g. LOW-VALUES) → typed hex | pad/truncate to n |
| `9(n)` / `9(n)V9(m)` DISPLAY | n+m bytes | digits only | zero-pad |
| `S9(n)V99` DISPLAY (zoned, overpunched) | n+2 bytes | ASCII: last byte `{`,`A`-`I` = +0..9, `}`,`J`-`R` = −0..9; EBCDIC: zone `C` +, `D` −, `F` unsigned/positive | preferred sign (`C`/`D` or overpunch) |
| `COMP-3` | ⌈(digits+1)/2⌉ bytes | nibbles, sign `C`/`F` +, `D` −; any other nibble → typed hex | `C`/`D` for signed, `F` for unsigned |
| `COMP` / `BINARY` / `COMP-4` | 2/4/8 bytes for 1-4/5-9/10-18 digits | big-endian two's complement if signed; |value| ≥ 10^digits → typed hex (truncation semantics) | big-endian |
| `COMP-5` | same sizes | native binary, full range allowed | big-endian |
| `REDEFINES` | shares storage | by discriminator field; unknown code → `UNKNOWN_BRANCH` hex | from the selected branch |
| `OCCURS n` | n × item | array of n objects | n slots |
| `FILLER` | n bytes | verbatim | verbatim |

### 4.3 ASCII vs EBCDIC

* `app/data/ASCII/*.txt` are **ASCII** line-sequential files: no packed or binary fields,
  signed amounts use ASCII overpunch; some lines are shorter than LRECL (trailing spaces
  trimmed, e.g. `cardxref.txt` 36 of 50 bytes) and three files use CRLF. The decoder strips
  CR, right-pads with spaces, and records both facts in the manifest.
* Files produced by the COBOL programs on z/OS (and `app/data/EBCDIC/*`) are **EBCDIC**
  (CP037) fixed-block; zoned signs are zone nibbles, and COMP/COMP-3 are real binary.
  Collating sequence differs (digits sort after letters in EBCDIC) — affects
  `>=`/`<=` comparisons on alphanumeric keys and SORT order, so L2 SORT steps are compared
  under the EBCDIC collating sequence.
* The EBCDIC seed counterparts are not identical to the ASCII seeds: account record 49
  (`ACCT-ADDR-ZIP`) and disclosure-group record 34 (`DIS-INT-RATE` 0.00 vs 15.00) differ.
  These are declared in `manifest.json` (`ebcdicCounterpart.divergentRecords`); tests
  accept exactly those differences and nothing else.

## 5. Seed-data observations that shape the tests

* All 50 ASCII account records have a blank `ACCT-GROUP-ID`; the disclosure-group code
  (`A000000000`) sits in the `ACCT-ADDR-ZIP` slot. Decoding stays strict per copybook, so
  `acctdata → discgrp` referential integrity reports 50 orphans. Behaviorally this means
  `CBACT04C` always falls back to the `DEFAULT` group for this seed data — the interest
  tests must include fixtures with a populated group ID to cover the primary lookup path.
* `tcatbal` balances are all zero, so interest on seed data is zero; L1 interest cases use
  synthetic non-zero balances.
* Export sequence numbers run 1..509 with 9 gaps (manifest) — counts reconcile on records,
  not on max sequence.
* Fillers in `tcatbal`, `discgrp`, `trantype`, `trancatg` contain `'0'` characters, not
  spaces — a migrated writer that blanks FILLER fails the byte round trip.

## 6. Edge-case catalog

| Format / area | Edge cases |
|---|---|
| Zoned `S9(n)V99` | max `9…9.99` and min `-9…9.99`; `0.00`, `-0.00` (negative zero must be preserved or normalized per decision record); every overpunch char `{ A-I } J-R`; unsigned digit in signed field (accepted, flagged non-preferred); invalid last byte (space, `x'00'`) → typed hex |
| COMP-3 | sign nibbles `C`, `D`, `F`, and invalid `A`/`B`/`E`; non-digit nibble; negative zero `x'…0D'`; even digit counts (pad nibble) |
| COMP/COMP-5 | 2/4/8-byte boundaries; values ≥ 10^digits (COMP truncates, COMP-5 does not); negative in unsigned field |
| Alphanumeric | LOW-VALUES/HIGH-VALUES; embedded control chars; non-CP037-mappable chars; trailing-space trimming on ASCII lines |
| Keys | leading zeros (`ACCT-ID 00000000001`); numeric key compared as text vs number; duplicate keys; composite keys (`TRAN-CAT-KEY`, `DIS-GROUP-KEY`) with blank parts |
| Dates | `X(10)` with invalid dates (`2023-02-30`), leap days (`2024-02-29`, `1900-02-29` invalid, `2000-02-29` valid), `0000-00-00`, blanks; timestamps compared via `(1:10)` substring |
| Arithmetic | intermediate overflow without `ON SIZE ERROR` (high-order truncation); `COMPUTE` without `ROUNDED` (truncation toward zero, e.g. `CBACT04C` interest); scale of intermediate results |
| Files | empty input file (no header in CBTRN03C, RC 0); single record; file missing (status 35 → abend); short records; record-length mismatch |
| Group-break logic | unsorted input; same card in two non-adjacent runs; card change exactly at page boundary; account totals at line 19/20 |
| REDEFINES | wrong discriminator (`EXPORT-REC-TYPE` unknown → error path in `CBIMPORT`); decoding the wrong branch (customer bytes as account: must fail field domain checks); `TWO-BYTES-BINARY`/`ALPHA` view |
| Online | `EIBCALEN = 0` first entry; PF3/PF7/PF8/ENTER/invalid AID; optimistic-lock conflict in `COACTUPC`/`COCRDUPC`; NOTFND/DUPREC RESP codes |

## 7. Phase scoping

| Phase | Scope | Fixtures |
|---|---|---|
| **1 — Core VSAM/batch** (this harness) | `app/cbl`, `app/cpy`, `app/jcl`, nine VSAM datasets + EXPORT | `golden_data/` |
| **2 — Authorization (IMS/DB2/MQ)** | `app/app-authorization-ims-db2-mq` (`CBPAUP0C`, `COPAUA0C`, `COPAUS0-2C`, `PAUDBLOD`/`PAUDBUNL`/`DBUNLDGS`; IMS DBDs/PSBs, `AUTHFRDS` DB2 table, MQ request/response) | separate `golden_data/authorization/` built from its `data/EBCDIC` IMS unload with copybooks `CIPAUSMY`/`CIPAUDTY`/`CCPAURQY`/`CCPAURLY`; DB2 rows as JSON; MQ messages as captured payloads |
| **3 — Transaction type (DB2)** | `app/app-transaction-type-db2` (DB2-backed TRANTYPE/TRANCATG maintenance; `ddl`, `dcl`, `ctl`) | separate `golden_data/transaction-type-db2/` from DB2 unloads; parity with the VSAM lookups of phase 1 |
| (later) VSAM-MQ | `app/app-vsam-mq` | own fixtures |

Each phase reuses the codec/compare/recon layers and adds its own layouts and fixtures;
no phase-2/3 fixture is mixed into phase-1 golden data.

## 8. Plugging in the migrated application

The integration point is `com.carddemo.harness.app.MigratedAppAdapter` (marked
`MIGRATED-APP INTEGRATION POINT`). The default `NotYetAvailableAdapter` makes
`MigratedAppParityTest` skip. To connect the app, implement the adapter (run a job / point
at its output files) in a separate module and run with
`-Dcarddemo.app.adapter=<fully.qualified.AdapterClass>`. The harness stays independent of
application classes: it only exchanges files and records. See `test_harness/README.md`.
